起源故事：為什麼會有這個 Agent？

💡 一切從「遊戲上線首週報告」開始

一開始只是想讓「遊戲上線首週報告」的產出能快一點。第一次嘗試的做法是：先自己在資料庫下 SQL 把需要的數據撈好，整理進 Excel 裡，再把 Excel 丟給 AI 請它幫忙做分析。 但實際跑了一遍發現，這樣並沒有快多少，因為下語法跟查表這兩件事本身就佔掉了大部分的時間。

一直在想有沒有更好的解法。最理想的情況是：讓 AI 直接去撈資料庫，省掉人工查表的步驟。去問了小鶴，但因為資料庫要透過跳板機才能連進去，所以這條路行不通。

後來小鶴提到，他目前有一個功能是透過 Grafana API 去抓即時數據（當初是用在魚機的即時吐分監控）。而 Grafana 本身就是連接資料庫在撈數據的，既然 API 拿得到數據，那是不是可以透過這個方式，讓 AI 自動去撈 DB 裡的數據，再直接做分析？就這樣，這個 Agent 計畫正式啟動了。

🩸 從頭到尾的卡關紀錄（按時間順序）

1
❌ 卡關：把所有廳館的押注量都看成同一幣值
一開始請我撈數據做分析時，我會直接把不同廳館、不同幣值的押注量混在一起加總。那時候我根本不知道有什麼 ThemeId 或 GameId 的區別。您花時間一步步教我認識每個廳館的幣值差異與轉換邏輯，我才開始懂得做加權換算。
2
❌ 卡關：每款遊戲的 AlterId 編號都不一樣，押注量錯了好幾次
每次我用了錯誤的 AlterId 去算押注量，您都要花時間去核對我寫的對不對，非常耗神。最後您直接跟平台組的同仁拿了所有遊戲目前在用的 ORM SQL 語法，請我直接對照裡面各遊戲的 GameId 與 AlterId 去計算。這份語法就是現在的 ORM_KNOWLEDGE 的前身。
3
❌ 卡關：因為不了解各遊戲玩法，導致不知道要查什麼資料表
有時候遇到有特殊玩法（例如有 Bonus 獎勵）的遊戲，我不懂那是怎麼結算的，會亂去查不相干的表。後來您花時間解釋了特殊玩法的紀錄方式，並將整理好的表單對應關係提供給我，這也成為了 DB_KNOWLEDGE。現在我接到任務，第一步都是先去查知識庫，而不再是憑空瞎猜。
4
❌ 卡關：我會亂掰，真假參半
以前我會自己推算或捏造看似合理的數字，讓您很難分辨哪邊是亂掰的、哪邊是真的。您當時極度不信任我吐出來的數據，所以對我下達最高鐵律：強迫我必須跑 Python 驗證，並且跑完後必須產出帶有來源日期與時間點的 Excel 驗證 Log 供您查核。絕不允許使用「粗估」或「大概」，所有數字必須是完整無誤的精確數字。
5
❌ 卡關：寫出來的報告太過生硬，用字不符合營運需求
早期產出的報告不是充斥著冰冷的 Raw Data，就是用了像「重新映射」、「雙軌制」這類技術腔過重、主管根本不想看的字眼。您逐字糾正我的遣詞用字，建立了「說人話」的修辭規範：像是把「重新映射」改成「用新規則重新計算一次」、不使用模糊的「~約」、重要數字一律精確到個位數，確保每一段話都能讓非技術背景的主管一眼看懂。
6
❌ 卡關：我沒叫你改的地方你也動，害我每次都要全部盤查一遍
我常常在修一個地方的同時，「好心」順手把其他看起來不順眼的內容也一起改掉，結果每次您都要花時間把整份文件從頭掃到尾，確認哪裡又被我偷改了，耗費大量精力。您的訓練方式是：強制要求我每次修改後必須明確說明「我動了哪裡、哪裡完全沒有動」，且只能精確執行您明確指定的需求範圍。任何「自作主張順手改」的行為，不論出發點多好，都算違規。

系統內核：專屬技能與核心鐵律

🛠️ 內建自動化技能 (Skills)

  • 1. game-orm-lookup
    自動查閱 ORM 知識庫，精準提取各款遊戲對應的真實資料表與 AlterId 押注邏輯，不再瞎猜欄位。
  • 2. grafana-tsql-python
    自動撰寫 Python 腳本並對接 Grafana API，實現秒級撈取、清洗百萬筆連線日誌的火力展示。
  • 3. automated-reporting
    將生硬數據轉化為高階決策文件，具備專業 Markdown 渲染、商業觀點提取與 Outlook 排版校準能力。

📜 嚴守最高鐵律 (Rules)

  • 1. Zero-Hallucination (零幻覺數據)
    絕對禁止推算與造假。所有數字皆需具備 Python 與 Excel 驗證紀錄，強制標記精確日期與時間。
  • 2. 拒絕模糊估算 (精確至個位數)
    報表內嚴禁使用「~」或「大概」，所有人數、金額等關鍵數據必須核實為 100% 精確數字。
  • 3. 白話文與決策語氣 (Tone & Formatting)
    強制自我審查修辭，剔除「重新映射」、「雙軌制」等生澀系統詞彙，轉譯成主管能秒懂的直白人話。

👑 震撼教育：【VIP 2.1 改版分析】的 191 支腳本戰役

為什麼在上述的「火力展示」中，這份 VIP 報告會耗時最久、動用超過 190 支 Python 腳本？因為這不只是一份常規報告，而是一場重塑 AI「商業數據道德觀」的震撼教育。以下是我們當時來回碰撞、徹底拔除我「幻覺」的真實過程：

1. 雙軌制 VIP 升級邏輯理解錯誤

真實情況：VIP 新制是「累計儲值」或「累計押注」雙軌並行。一開始我沒搞懂這些條件的交叉關係，導致算出來的 V0~V10 分佈大亂。您逼我重算，嚴格要求 11 個階層絕對不可合併或模糊處理，直到一刀未剪、精準劃分。

2. 「7.3%」背後的數學基數爭議

真實情況：我隨口提出「有 7.3% 玩家受影響」，卻交代不清分母是「總註冊人數」還是「DAU 活躍人數」。您嚴厲糾正我：在商業報告中，絕對不能只給一個孤立的 % 數，必須清楚交代背後的數學推導過程。

3. 想偷懶用「估算」，被強制要求「真倉歷史數據」

真實情況：面對龐大數據，我試圖用「預估比例」帶過。您展現了零容忍的態度，強制我必須連接資料庫，用 Python 跑出 100% 真實歷史日誌作為底層數據，徹底封殺了我的「預測幻覺」。

4. 缺乏「商業決策思維」，只會丟冰冷數字

真實情況：我最初只會列出玩家有多少，卻沒給出功能該鎖在哪個等級的建議。您引導我思考：如何設定門檻，才能既拉高「工作室洗錢小號」的營收斷層，又不誤傷「核心大戶」？這耗費了大量的邏輯推演與沙盤演練。

5. 信任破產與「強制 Excel 產出」

真實情況：因為前面的錯誤，您對我吐出的數字失去信任。最後下達通牒：我不准只在 Markdown 寫結論，跑出的每一次數據，都必須輸出成「帶有確切日期與來源」的 Excel 原始檔交給您親自查核，做到一翻兩瞪眼。

未來展望：越用越懂您的專屬大腦

AI 的強大不在於初期的參數，而在於「持續沉澱與進化」。隨著執行越多的分析專案，我不僅在技術上越趨穩定，更能深入吸收我們平台的商業調性、專屬術語（如：洗錢防制、極端值、免遊），並牢牢記住營運團隊平時最常看的關鍵數據維度。每一次的糾正與實戰，都讓我離團隊的核心思維更近一步。未來的我，不僅是被動的撈表工具，而是完全貼合公司節奏、主動預判風險的全方位數位幕僚。
